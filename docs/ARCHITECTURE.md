# معماری فنی — چرا (Chera) — AI Data-to-Decision Copilot

این سند معماری فعلی (MVP) و مسیر رشد محصول را توضیح می‌دهد.

## ۱. خلاصهٔ محصول

«چرا» داده‌های جدولی شرکت (فروش، هزینه، عملیات) را می‌گیرد و به سؤال‌های فارسی
دربارهٔ آن داده جواب می‌دهد: تجمیع ساده، مقایسه به تفکیک یک بُعد، روند زمانی، و
مهم‌تر از همه — تجزیهٔ «چرا یک شاخص تغییر کرد» به سهم هر دسته در آن تغییر.

## ۲. اجزای فعلی (MVP)

```
┌─────────────┐      HTTP/JSON      ┌──────────────────┐
│  Frontend   │ ───────────────────▶│  FastAPI Backend  │
│ (Vanilla JS,│◀─────────────────── │                    │
│  Chart.js)  │                     │  ├─ datastore.py   │  ← آپلود/ذخیره دیتاست
└─────────────┘                     │  ├─ nlu.py         │  ← تحلیل سؤال فارسی
                                     │  ├─ analytics.py   │  ← موتور تجمیع/تحلیل
                                     │  ├─ jalali.py       │  ← تبدیل تاریخ شمسی
                                     │  └─ schemas.py      │  ← مدل‌های API
                                     └──────────┬─────────┘
                                                │ pandas DataFrame (in-memory + pickle on disk)
                                                ▼
                                     backend/data/*.pkl + manifest.json
```

- **Frontend**: HTML/CSS/JS خالص، بدون فریم‌ورک و بدون مرحلهٔ build؛ از همان
  FastAPI به‌صورت static سرو می‌شود (`app.mount("/", StaticFiles(...))`). این
  انتخاب عمدی است: برای MVP سرعت توسعه و صفر-وابستگی به ابزار build مهم‌تر از
  انعطاف یک SPA کامل بود. اگر تیم محصول در آینده به کامپوننت‌بندی پیچیده نیاز
  داشت، مهاجرت به React/Vite گام بعدی طبیعی است.
- **Backend**: FastAPI + pandas. هیچ وابستگی به LLM خارجی در مسیر پاسخ‌دهی
  فعلی نیست — یک موتور تحلیل قانون‌محور (`nlu.py`) الگوهای رایج سؤال فارسی را
  تشخیص می‌دهد و مستقیم روی DataFrame اجرا می‌کند. این یعنی هزینهٔ صفر و تأخیر
  خیلی کم برای دسته‌ی رایج سؤال‌ها، اما پوشش محدودتر از یک LLM آزاد.
- **ذخیره‌سازی**: هر دیتاست به‌صورت `pandas.DataFrame.to_pickle` روی دیسک ذخیره
  می‌شود؛ یک مانیفست JSON فهرست دیتاست‌ها را نگه می‌دارد. این تصمیم عمدی برای
  MVP تک‌کاربره/تک‌سرور است، **نه برای production چندمستأجری**.

## ۳. موتور NLU فارسی — چرا rule-based، نه LLM؟

برای MVP یک NLU قانون‌محور نوشته شده (`backend/app/nlu.py`) که:

1. نام ستون‌ها را در متن سؤال با نرمال‌سازی فارسی (`textnorm.py`: یکسان‌سازی
   ی/ك، اعداد فارسی/عربی به لاتین، حذف اعراب) پیدا می‌کند.
2. کلیدواژه‌های تابع تجمیع را تشخیص می‌دهد: میانگین/مجموع/بیشترین/کمترین/تعداد.
3. الگوهای «چرا … افت/رشد کرد» را به تحلیل `explain_change` مسیر می‌دهد.
4. الگوهای «روند» را به `trend_by_period` مسیر می‌دهد.

**مزیت**: بدون هزینهٔ API، بدون تأخیر شبکه، رفتار قابل‌پیش‌بینی و قابل تست
واحد (نگاه کنید `backend/tests/test_nlu.py`).

**محدودیت شناخته‌شده**: سؤال‌های آزاد، چندمرحله‌ای یا مبهم (مثلاً «مشتری‌های
VIP که کمتر از حد معمول خرید کردن رو نشون بده») را پوشش نمی‌دهد.

### گام بعدی NLU
لایهٔ `parse_question` طوری طراحی شده که با یک لایهٔ جایگزین یا مکمل مبتنی بر
LLM ترکیب شود:
1. اول موتور قانون‌محور را امتحان کن (سریع، رایگان).
2. اگر intent برگشتی `fallback` بود، سؤال + schema دیتاست (نام ستون‌ها، نوع
   داده، چند سطر نمونه) را به یک LLM بده تا کد pandas/SQL امن تولید کند (با
   sandboxing و whitelist توابع مجاز — **هرگز اجرای مستقیم کد آزاد کاربر یا
   خروجی مدل بدون sandbox**).
3. نتیجه را در همان قالب `AskResponse` برگردان تا فرانت‌اند تغییری نخواهد.

## ۳.۱ موتور بینش خودکار (Insight Engine) — گام اول فاز ۴

علاوه بر `nlu.py` که به سؤال صریح کاربر جواب می‌دهد، `backend/app/insights.py`
بدون نیاز به هیچ سؤالی، مستقیم روی دیتافریم اجرا می‌شود و مهم‌ترین یافته‌ها را
خودش پیدا می‌کند — اولین قدم از «هشدار پیش‌فعال» در نقشهٔ راه (بخش ۸، فاز ۴).
کاملاً قانون‌محور و بدون هزینهٔ API، هم‌راستا با فلسفهٔ `nlu.py`.

چهار نوع یافته تشخیص داده می‌شود:

1. **روند (trend)**: تغییر دوره‌به‌دورهٔ بیش از ۲۰٪ در یک سنجهٔ عددی.
2. **تمرکز (concentration)**: یک دستهٔ خاص بیش از ۵۰٪ مجموع یک سنجه را به خود
   اختصاص داده (ریسک وابستگی).
3. **گروه دورافتاده (outlier_group)**: میانگین یک دسته با z-score بالای ۲
   نسبت به بقیهٔ دسته‌های همان بُعد فاصله دارد.
4. **کیفیت داده (data_quality)**: بیش از ۲۰٪ مقدار خالی در یک ستون.

خروجی، حداکثر ۵ یافته (`MAX_INSIGHTS`) مرتب‌شده بر اساس شدت/اهمیت است و از
مسیر `GET /api/datasets/{id}/insights` در دسترس فرانت‌اند قرار می‌گیرد؛
فرانت‌اند این یافته‌ها را بلافاصله بعد از انتخاب دیتاست به‌صورت یک پیام
خودکار در چت نمایش می‌دهد (`app.js: loadInsights`).

**گام بعدی طبیعی**: افزودن هشدار «فعال» (polling/webhook وقتی دیتاست جدید
آپلود می‌شود، نه فقط وقتی کاربر دیتاست را باز می‌کند) و پیشنهاد اقدام کنار هر
یافته — نگاه کنید بخش ۸.

## ۴. تقویم شمسی — یک تصمیم طراحی مهم

داده‌های ایرانی معمولاً تاریخ شمسی دارند (مثلاً `۱۴۰۳/۰۱/۰۵`). چون
`pandas.Timestamp` فقط سال‌های میلادی ۱۶۷۷ تا ۲۲۶۲ را پشتیبانی می‌کند، این
تاریخ‌ها باید قبل از هر تحلیل به میلادی تبدیل شوند (`jalali.py`, با کتابخانهٔ
`jdatetime`). نکتهٔ ظریف‌تر: چون ماه‌های شمسی و میلادی هم‌مرز نیستند، گروه‌بندی
«ماهانه» برای گزارش کسب‌وکار ایرانی باید روی مرز واقعی ماه شمسی انجام شود، نه
`dt.to_period("M")` میلادی — این نکته در `analytics.py` و تست‌های مربوطه رعایت
شده است.

## ۵. منابع داده — وضعیت فعلی و مسیر رشد

| مرحله | وضعیت | توضیح |
|---|---|---|
| آپلود CSV/Excel | ✅ در MVP | حداکثر ۲۵ مگابایت، ۲۰۰,۰۰۰ سطر |
| اتصال مستقیم دیتابیس (Postgres/MySQL) | roadmap | connector با read-only credential |
| اتصال Google Sheets | roadmap | برای تیم‌هایی که داده‌شان در شیت است |
| اتصال CRM (مثلاً دیدار، پیام‌گستر) | roadmap | نیاز به API adapter اختصاصی هر CRM |
| Data warehouse (BigQuery/ClickHouse) | roadmap برای مشتریان بزرگ | برای حجم داده‌ی بزرگ‌تر از حافظه |

لایهٔ `datastore.py` عمداً پشت یک اینترفیس ساده (`load_dataframe`,
`save_upload`) نگه داشته شده تا جایگزینی merge/backend ذخیره‌سازی (مثلاً
DuckDB روی فایل‌های Parquet، یا اتصال زندهٔ دیتابیس) بدون تغییر در `analytics.py`
و `nlu.py` ممکن باشد.

## ۶. امنیت و چندمستأجری بودن (نکات برای production)

MVP فعلی **تک‌کاربره و بدون احراز هویت** است — مناسب دمو و اعتبارسنجی محصول،
نه استقرار عمومی. قبل از production واقعی حتماً باید اضافه شود:

- **احراز هویت و مالکیت داده**: هر دیتاست باید به یک `workspace_id`/`user_id`
  متصل باشد؛ کوئری‌ها فقط باید روی دیتاست‌های همان تنانت اجرا شوند.
- **رمزنگاری در حالت سکون**: فایل‌های آپلودی شرکت‌ها می‌تواند حاوی داده‌ی مالی
  حساس باشد؛ storage باید encrypted باشد (مثلاً S3 + SSE، یا دیسک رمزنگاری‌شده).
- **Rate limiting و سقف حجم**: در MVP سقف ۲۵MB/۲۰۰k سطر برای جلوگیری از
  مصرف بی‌رویهٔ حافظهٔ سرور گذاشته شده؛ در production باید صف پردازش
  (background worker) برای فایل‌های بزرگ‌تر اضافه شود.
- **Audit log**: چه کسی چه سؤالی از چه داده‌ای پرسیده، برای انطباق سازمانی.
- اگر لایهٔ LLM اضافه شد: **هرگز داده‌ی خام مشتری را بدون رضایت به یک ارائه‌دهندهٔ
  LLM خارجی نفرست** بدون بررسی قرارداد پردازش داده (DPA) و در نظر گرفتن
  گزینه‌ی مدل self-hosted برای مشتریان حساس به حریم داده.

## ۷. تست‌ها

- `backend/tests/test_analytics.py`: صحت توابع تجمیع، گروه‌بندی، تجزیهٔ تغییر و
  روند زمانی (با تاریخ شمسی واقعی).
- `backend/tests/test_nlu.py`: تشخیص درست intent از روی سؤال فارسی، شامل یک
  رگرسیون‌تست مهم که «کمترین فروش کدام کانال» را به «کمترین **مجموع** فروش»
  (نه کوچک‌ترین تک‌رکورد) مسیر می‌دهد.

اجرا: `cd backend && .venv/bin/python -m pytest tests/ -v`

## ۸. نقشهٔ راه پیشنهادی

1. **فاز ۱ (فعلی)** — MVP تک‌کاربره: آپلود فایل + NLU قانون‌محور + توضیح تغییر.
2. **فاز ۲** — احراز هویت چندکاربره، ذخیره‌سازی دائمی (Postgres برای متادیتا +
   DuckDB/Parquet برای داده)، تاریخچهٔ گفتگو.
3. **فاز ۳** — لایهٔ LLM مکمل برای سؤال‌های خارج از پوشش rule-based، با
   sandbox اجرای کوئری.
4. **فاز ۴** — اتصال مستقیم به منابع داده‌ی زنده (دیتابیس شرکت، CRM، شیت)،
   هشدار پیش‌فعال («فروش امروز ۲۰٪ کمتر از میانگین است»)، و پیشنهاد اقدام.
   ✅ گام اول (موتور بینش خودکار قانون‌محور روی دیتاست‌های آپلودشده) پیاده‌سازی
   شد — بخش ۳.۱ را ببینید. باقی‌ماندهٔ این فاز: هشدار زنده/webhook و پیشنهاد اقدام.
5. **فاز ۵** — چندمستأجری کامل، RBAC، audit log، و گزینهٔ استقرار on-premise
   برای مشتریان حساس به داده.
